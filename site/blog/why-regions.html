Why regions

2026-08-10

Every systems language answers one question first: who owns memory? The industry's two mainstream answers are both unsatisfying.

Manual management gives you control and predictability, at the cost of use-after-free, double-free, and leaks. Tracing garbage collectors remove those bugs, but introduce pauses, overhead, and a runtime you cannot turn off.

Bedrock picks a third answer: regions. A region block introduces an arena. Composite values declared inside it live there. When the block exits, everything is reclaimed at once — one pointer bump, no tracing, no finalizers.

region R
    var p = Person(id = 0, age = 24)
end   // everything in R is gone, instantly

The obvious objection: what stops a value from escaping its region and dangling? A single rule, checked at compile time — the escape rule. A reference may only flow from a region into a region that closes no sooner. Regions nest, so this is plain ancestry checking, not a borrow-checker puzzle.

region R
    var p1 = Person(id = 0, age = 24)
    region I
        var p2 = Person(id = 0, age = 24)
        p1 = p2    // compile error: I closes before R
    end
end

When a value must outlive its region, you say so explicitly — either by returning by value (which copies out), or with new(@lifetime) promotion.

The result is a language with no manual memory management in ordinary code, no garbage collector, and no runtime surprises. Just allocations that end exactly when you expect them to.
